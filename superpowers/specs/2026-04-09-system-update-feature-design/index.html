    System Update Feature Design¶

    Date: 2026-04-09 Status: Approved — superseded as a description of the running system Author: Claude Code

    Read the reference page, not this, for how it works today

    This is the original design. Much of what it describes was later found broken in the field and rebuilt: the update daemon was never installed, the web path never pulled, the DB and uploaded files were lost to the stash, and the update scripts could not ship their own changes. Update System documents the system as it is now. This file is kept for the design history.

    Overview¶

    Add a system update feature to the Tinko web interface that allows authenticated users to check for and apply updates from the settings page. The feature uses a separate systemd service to handle updates, ensuring the process survives the main Django service restart.

    Requirements¶

    1. Access: Any authenticated user can trigger updates
    2. Location: New "Updates" tab in the settings page
    3. Feedback: Real-time progress via WebSocket + staged progress indicator + detailed logs
    4. Auto-refresh: Page refreshes 10 seconds after successful update
    5. Error handling: Show error with retry button on failure
    6. User control: Two buttons - "Check for Updates" and "Update Now"
    7. Confirmation: Simple confirmation dialog before starting update

    Key Design Decision¶

    The update daemon runs as a separate systemd service (root) that survives the Django service restart. Status is written to a file (/run/tinko-update/status.json) which persists across restarts and can be read by Django when it comes back online.

    The daemon executes the existing update.sh script. To enable real-time telemetry, update.sh is modified to write its current stage to the status file. The daemon monitors the status file and streams these updates via WebSocket/REST to the frontend.

    Update Flow¶

    Check for Updates¶

    User clicks "Check for Updates"
        │
        ▼
Django runs: git fetch && git log HEAD..origin/main --oneline
        │
        ▼
Returns: { available: true, commits: ["abc123 Fix bug", "def456 Add feature"] }
        │
        ▼
Frontend shows: "Update available (2 commits ahead)"

    Start Update¶

    User clicks "Update Now"
        │
        ▼
Confirmation dialog: "This will restart the service. Continue?"
        │
        ▼ [confirmed]
Django creates UpdateStatus record (status=in_progress)
Django writes trigger file: /run/tinko-update/trigger
Django responds with { update_id: "uuid" }
Frontend opens WebSocket connection
        │
        ▼
[Service continues running - WebSocket streams logs]
tinko-update.service detects trigger file
tinko-update.service runs update.sh
        │
        ▼ [stage: "stop_service"]
update.sh: sudo systemctl stop tinko
        │
        ▼ [WebSocket DISCONNECTS]
Frontend shows: "Reconnecting..." with spinning indicator
        │
        ▼
Frontend polls: GET /api/updates/status/
        │ (returns error - server down)
        ▼
Frontend waits, polls again every 2 seconds
        │
        ▼ [after ~20-60 seconds, Django returns]
Frontend receives: { status: "completed", stage: "restart" }
        │
        ▼
Frontend shows: "Update complete!" + 10 second countdown
        │
        ▼
Page refreshes automatically

    Progress Stages¶

    1. check_git - Verify git repository
    2. stop_service - Stop tinko.service
    3. pull - Git pull latest changes
    4. dependencies - uv sync dependencies
    5. migrations - Run database migrations
    6. static - Collect static files
    7. translations - Compile translations
    8. wifi_connect - Update wifi-connect files
    9. restart_service - Restart tinko.service

    Edge Cases¶

    Scenario Behavior
    Service never restarts Frontend polls for 5 minutes, then shows "Update may have failed. Check logs or SSH in."
    Status file corrupted Daemon recreates status file, marks as failed with "Status file corrupted"
    Another update in progress Show "Update already in progress" with current progress
    Network failure during pull Mark stage as failed, offer retry button
    Merge conflicts Mark as failed with message about manual resolution needed
    Trigger file exists on boot Daemon processes it (handles interrupted updates)

    Daemon Startup Recovery¶

    tinko-update.service starts
        │
        ▼
Check for leftover trigger file
        │
        ├─ [found] ──▶ Check status.json
        │                    │
        │                    ├─ [in_progress] ──▶ Resume/finish update
        │                    └─ [completed/failed] ──▶ Clean up trigger
        │
        └─ [not found] ──▶ Wait for new trigger

    WebSocket Disconnect Handling¶

    // Frontend behavior when WebSocket closes
let reconnectAttempts = 0;
const maxReconnectAttempts = 150; // 5 minutes at 2-second intervals

ws.onclose = (event) => {
    showReconnectingState();
    pollStatusWithBackoff();
};

function pollStatusWithBackoff() {
    fetch('/api/updates/status/')
        .then(response => response.json())
        .then(data => {
            if (data.status === 'completed') {
                showSuccessAndRefresh();
            } else if (data.status === 'failed') {
                showErrorWithRetry(data.error);
            } else {
                updateProgress(data);
                setTimeout(pollStatusWithBackoff, 2000);
            }
        })
        .catch(() => {
            reconnectAttempts++;
            if (reconnectAttempts < maxReconnectAttempts) {
                setTimeout(pollStatusWithBackoff, 2000);
            } else {
                showManualInterventionNeeded();
            }
        });
}

    Security¶

    Access Control¶

    Endpoint Access
    GET /api/updates/check/ @login_required - Any authenticated user
    POST /api/updates/start/ @login_required - Any authenticated user
    GET /api/updates/status/ @login_required - Any authenticated user
    WebSocket /ws/updates/ Authenticated via AuthMiddlewareStack

    Security Measures¶

    1. Trigger file permissions - Written to /run/tinko-update/ which requires root. The daemon (running as root) has write access.

    2. Status file permissions - Readable by all, writable only by root daemon.

    3. Command sanitization - No user input passed to shell. The daemon only runs the hardcoded update.sh script.

    4. Rate limiting - Prevent update spam with minimum 5-minute interval between updates (tracked in database).

    5. Audit logging - All update attempts logged with user and timestamp.

    6. Sudoers Configuration - The tinko user must have passwordless sudo access for systemctl and cp/chmod/chown commands used in update.sh to ensure the script can be triggered from the Django context if necessary, although the daemon itself runs as root.

    Rate Limiting Implementation¶

    # core/update_system/views.py

@login_required
def start_update(request):
    # Check rate limit
    last_update = UpdateStatus.objects.filter(
        status__in=['completed', 'in_progress']
    ).order_by('-started_at').first()

    if last_update and last_update.started_at > timezone.now() - timedelta(minutes=5):
        return JsonResponse({
            'error': 'Updates can only be run every 5 minutes',
            'next_update_at': last_update.started_at + timedelta(minutes=5)
        }, status=429)

    # Check for in-progress update
    if UpdateStatus.objects.filter(status='in_progress').exists():
        return JsonResponse({
            'error': 'Update already in progress'
        }, status=409)

    # Create update record
    update = UpdateStatus.objects.create(
        user=request.user,
        status='in_progress'
    )

    # Write trigger file
    write_trigger_file(update.id)

    return JsonResponse({'update_id': update.id})

    Version Display¶

    The current version shown in the UI comes from git describe --tags which produces version strings like v1.2.3 or v1.2.3-5-gabc123 if there are untagged commits. This is displayed as "Current Version: v1.2.3" in the Updates tab.

    Daemon Process Flow¶

    # update_daemon.py (simplified)

def main():
    ensure_status_file_exists()
    recover_interrupted_update()

    while True:
        if trigger_file_exists():
            update_id = read_trigger_file()
            run_update(update_id)
            cleanup_trigger_file()

        time.sleep(1)

def run_update(update_id):
    stages = [
        ('check_git', check_git_repo),
        ('stop_service', stop_service),
        ('pull', git_pull),
        ('dependencies', update_dependencies),
        ('migrations', run_migrations),
        ('static', collect_static),
        ('translations', compile_translations),
        ('wifi_connect', update_wifi_connect),
        ('restart_service', restart_service),
    ]

    for stage_name, stage_func in stages:
        update_status(stage_name, 'in_progress')
        try:
            output = stage_func()
            log_output(output)
            mark_stage_complete(stage_name)
        except Exception as e:
            mark_failed(stage_name, str(e))
            return

    mark_completed()
